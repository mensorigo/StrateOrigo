# ADR-0001 · 策略进程模型：策略如何独立开发、运行、暂停和退出

- 状态：**已决策**（2026-11-08）
- 日期：2026-11-08
- 影响范围：`so-trader` 进程划分、`so-portfolio` 预算落地方式、账户级风控、部署方式、交易所账户结构

## 1. 背景与需求

需求原文：**不同策略可以独立开发、运行、暂停和退出。**

拆开来是四个具体要求：

| # | 要求 | 含义 |
|---|---|---|
| R1 | 独立开发 | 新增或修改一个策略的代码，不需要动其他策略 |
| R2 | 独立部署 | 上线 / 升级一个策略，**不中断**其他正在运行的策略 |
| R3 | 独立运行控制 | 单个策略可以暂停、恢复、退出（平仓后停止） |
| R4 | 故障隔离 | 一个策略崩溃、死循环、亏损失控，不拖垮其他策略和整个账户 |

约束：
- 热路径延迟不能变差（每个策略的行情 → 下单路径仍在单进程内完成）。
- 账户级风控（总敞口、保证金率、总亏损）必须始终有效。
- 单人运维，复杂度要可控。

**现状设计**：所有策略编译进同一个 `so-trader` 进程。R1、R3 已满足（策略是独立 crate，生命周期有暂停/恢复/退出）；**R2、R4 不满足**：上线新策略代码需要重启整个进程，一个策略 panic 或卡死会影响同进程的所有策略。

## 2. 候选方案

### 方案 A：单进程多策略 + 重启式部署（原设计）
所有策略在一个进程，新代码上线时整体重启，依靠状态快照与对账快速恢复。
- ✅ 最简单；账户级风控在进程内实时、精确；行情只订阅一份。
- ❌ 每次部署所有策略中断数秒～数十秒；故障不隔离（R2、R4 不满足）。

### 方案 B：每策略一个进程，共享同一个交易账户
- ✅ 部署和故障隔离（R2、R4 满足）。
- ❌ 账户级风控需要跨进程汇总（守护进程或共享内存协调器），实时性变差。
- ❌ 多个进程交易同一品种时，交易所侧持仓合并在一起（单向持仓模式下），**无法从交易所数据区分各策略的持仓**，对账困难。
- ❌ 一个策略亏损消耗的是共享保证金，会影响其他策略的强平风险。

### 方案 C：每策略一个进程 + 每进程一个交易所子账户
- ✅ R1~R4 全部满足。
- ✅ **资金物理隔离**：子账户里只有分配给它的资金，即使策略和进程内风控同时出错，最大损失也被限定在该子账户内。
- ✅ 对账简单：一个子账户的持仓就是一个策略的持仓。
- ❌ 资金碎片化：每个子账户都要留保证金余量，资金利用率下降；需要定期划转再平衡。
- ❌ 运维对象变多：子账户、API Key、进程数量都随策略数增长。
- ❌ 每个进程各自订阅行情，连接数增加（可能触及交易所连接限制）。
- ⚠ 需要确认 OKX / Gate 的子账户数量上限、API 权限、划转规则、子账户交易量是否计入主账户手续费等级。

### 方案 D：单进程 + 动态插件（dylib / WASM 热加载）
策略编译为动态库（`abi_stable` 等 C ABI 封装）或 WASM 模块，运行时加载 / 卸载。
- ✅ 不重启进程即可上线新策略；行情只订阅一份；账户风控在进程内。
- ❌ Rust 没有稳定 ABI，dylib 方案需要严格的接口封装，出错时难以调试；WASM 有调用开销且限制内存访问方式。
- ❌ **不解决故障隔离**：插件崩溃或卡死仍会影响整个进程（WASM 可以隔离崩溃，但不能隔离 CPU 占用）。
- ❌ 实现复杂度最高。

### 方案 E：混合——"策略组"进程 + 子账户作为风险隔离单元
进程的划分单位是**策略组**（一组需要紧密协作的策略实例，例如做市 + 对冲），子账户的划分单位是**风险等级**。默认一个策略实例 = 一个进程 = 一个子账户（即方案 C），需要时可以把几个实例放进同一进程或同一子账户。
- ✅ 兼顾 C 的隔离性与 A 的灵活性；需要共享内存状态的策略可以放在一起。
- ❌ 规则比 C 多一层（要定义什么情况允许合组）。

## 3. 方案对比

| | A 单进程 | B 多进程共享账户 | C 多进程+子账户 | D 动态插件 | E 混合 |
|---|---|---|---|---|---|
| R1 独立开发 | ✅ | ✅ | ✅ | ✅ | ✅ |
| R2 独立部署 | ❌ | ✅ | ✅ | ✅ | ✅ |
| R3 独立控制 | ✅ | ✅ | ✅ | ✅ | ✅ |
| R4 故障隔离 | ❌ | 部分（进程隔离，资金不隔离） | ✅ | ❌ | ✅ |
| 账户级风控 | 实时、简单 | 跨进程汇总，较难 | 子账户天然隔离 + 主账户汇总 | 实时、简单 | 同 C |
| 同品种多策略对账 | 进程内归因 | **困难** | 简单 | 进程内归因 | 简单 |
| 资金利用率 | 高 | 高 | 较低 | 高 | 可调 |
| 行情连接数 | 1 份 | N 份 | N 份 | 1 份 | 按组 |
| 实现复杂度 | 低 | 中 | 中 | 高 | 中 |
| 运维复杂度 | 低 | 中 | 中高 | 低 | 中 |

## 4. 无论选哪种方案都需要的东西

- 策略实例生命周期（03 §4.2）、状态快照与恢复、Exit 平仓流程。
- systemd 模板单元 `so-trader@<instance>.service`（多进程方案）或进程内实例管理（单进程方案）。
- 守护进程 `so-guardian` 监控**所有实盘**进程与真实账户（含主账户汇总），不监控模拟盘。
- 行情连接数过多时的后备方案：本机行情分发进程，通过共享内存向各交易进程广播（第二阶段再做）。

## 5. 讨论过的问题（结论见 §6）

1. 预计**同时运行**多少个策略实例？（< 5 / 5~20 / > 20）——决定连接数、子账户数量是否成为瓶颈。
2. 是否会有**多个策略交易同一个品种**？——决定方案 B 是否可行。
3. 是否接受使用**交易所子账户**？——方案 C / E 的前提。
4. 新策略上线或更新的**频率**？（每周 / 每月 / 更少）——决定"重启式部署"的代价有多大。
5. 是否有需要**共享进程内状态**的策略组合（例如做市 + 跨所对冲）？——决定是否需要方案 E 的"合组"。

## 6. 决策

**采用"配置驱动的一账户一策略"模型**（方案 C 的简化版）：

1. **任何模式下，一个账户只运行一个策略实例。**
2. **实盘进程 = 一个真实账户 + 一个策略**（跨所策略为每个交易所各一个账户）。运行哪个交易所、哪个账户、哪个策略，全部由启动配置 `configs/env/<instance>.toml` 决定。
3. **启动时强制校验**：`live` / `demo` 配置中出现多个策略、或同一交易所出现多个账户，拒绝启动。
4. **多账户 / 多策略只用于测试验证**：在本地模拟盘 `paper` 进程中开任意多个虚拟账户，每个虚拟账户一个策略，不占用真实账户、不加载任何 API Key。
5. **需要第二个实盘策略时**：开一个交易所子账户 + 启动一个新的实盘实例（`so-trader@<instance>.service`）。各实例互不影响，可独立部署、暂停、退出。
6. **多模式可以同时运行**：实盘实例与模拟盘实例是独立进程（影子盘、新旧版本并行），安全规则见 [01 §7.2](../01-architecture.md)。

本地模拟盘配置示例：

```toml
# configs/env/paper-lab.toml
mode  = "paper"
venue = "okx"

[[accounts]]
id              = "sim-funding-v1"
initial_balance = 10000      # USDT
strategy        = "configs/strategies/funding-carry-v1.toml"

[[accounts]]
id              = "sim-funding-v2"
initial_balance = 10000
strategy        = "configs/strategies/funding-carry-v2.toml"
```

实盘配置示例：

```toml
# configs/env/live-okx-funding.toml
mode     = "live"
venue    = "okx"
account  = "okx-sub-funding"            # 只能有一个
key_file = "/etc/strateorigo/keys/okx-sub-funding.toml"
strategy = "configs/strategies/funding-carry-v1.toml"   # 只能有一个
```

### 6.1 需求满足情况

| 需求 | 如何满足 |
|---|---|
| R1 独立开发 | 策略是独立 crate |
| R2 独立部署 | 每个实盘策略是独立进程，升级一个不中断其他 |
| R3 独立控制 | 策略生命周期（03 §4.2）+ 进程级启停 |
| R4 故障隔离 | 进程隔离 + 子账户资金隔离；最大损失限定在该子账户内 |

### 6.2 理由

- 实际使用以**单账户单策略**为主，多策略并行只是为了验证，用虚拟账户即可，不需要在实盘进程里处理多策略的合并、冲突与资金归因。
- 一个账户的持仓就是一个策略的持仓，对账与盈亏归因最简单。
- 实盘进程内没有多策略，账户级风控就是策略级风控，规则更少、更不容易出错。

### 6.3 放弃的方案

| 方案 | 放弃原因 |
|---|---|
| A 单进程多策略（实盘） | 部署与故障不隔离；需要多策略冲突检测与预算分配，复杂度高 |
| B 多进程共享账户 | 交易所侧持仓合并，无法归因；共享保证金互相影响 |
| D 动态插件 | 复杂度最高且不解决故障隔离 |
| E 策略组合并 | 目前没有需要共享进程内状态的策略组合；需要时再开新 ADR |

### 6.4 后果

- 资金分散在多个子账户，利用率略降；跨账户资金调整为人工确认的子账户划转（03 §14）。
- 实盘实例增多后，行情连接数可能触及限制——届时实现本机行情分发进程（第二阶段）。
- 本地模拟盘中同一品种的多个虚拟账户不会互相争夺排队位置（01 §7.1），结果不能相加。
- 上线前需确认 OKX / Gate 子账户数量上限、API 权限与划转规则，写入 `docs/venues/`。
