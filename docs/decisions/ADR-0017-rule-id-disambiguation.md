# ADR-0017：规则编号去歧义（日志规则 L→G，领域级别加前缀）

- 状态：**已接受并已实施**（2026-11-12）
- 日期：2026-11-12
- 触发：ADR-0015 建立规则编号体系后复查，发现纯数字标识符没有作用域，`L` 前缀一名三用
- 相关：ADR-0015（编号体系）、ADR-0016（`so-journal`）

## 背景

ADR-0015 定下规则编号 `<字母><数字>`，其中 `L` = 日志（`L1`–`L6`）。
但项目里 `L` 还同时被三处领域概念占用：

| 占用者 | 出处 | 示例 |
|---|---|---|
| 日志规则 | [04 §3.6](../04-dev-constraints.md) | `L4` = 记录错误必须带 `code` |
| 风控执行位置 | [01 §10](../01-architecture.md)、[03 §7](../03-module-design.md) | `L1` 事前 / `L2` 组合 / `L3` 守护进程 |
| 订单簿深度 | [01 §1.3](../01-architecture.md)、[03 §1](../03-module-design.md) | `L1` 一档 / `L2` 多档（行业通用） |
| 回测保真度 | [03 §8.1](../03-module-design.md) | `L0` / `L1` / `L2` |

### 实际后果（不是理论洁癖）

1. **同一篇文档内自相矛盾**：`docs/04` 里 `§3.6` 的 `L4` 是日志规则，
   而 `§3.5` 开头整段在解释"风控的 L1/L2/L3、订单簿的 L1/L2、保真度 L0/L1/L2"。
   读者看到 `L4` 必须靠上下文猜是哪一个。
2. **编号失去检索价值**：规则编号的全部意义是"扫一眼就知道指向哪条规则"（04 §5.7）。
   `L2` 在 docs/01 指订单簿深度、在 docs/03 §8.1 指 Rust 事件驱动回测、
   在 docs/05 指组合风控线程——同一个符号三种所指。
3. **跨文件引用只能靠人脑解析**：`crates/so-telemetry/src/error.rs` 注释里写
   `docs/04 §3.6 L4`，而 `so-cli` 的 `exit.rs` 写 `docs/04 L4`。
   前者靠章节号消歧，后者没有章节号就歧义——但"代码注释只引用编号、不引用章节号"
   正是 ADR-0015 定的规矩，规矩与消歧手段互相冲突。

### 为什么改日志规则而不是改领域编号

`L1`/`L2` 作为**订单簿深度**是行业通用术语（L1 = top of book，L2 = aggregated depth），
改掉会平白制造与外部文档（交易所 API、hftbacktest、Tardis）的翻译成本。
风险与回测的 `L0/L1/L2` 语义上都可归约为"订单簿深度或撮合精细度"，
可以**继承订单簿的 `L`**、只加领域前缀。

反过来，日志规则 `L1`–`L6` 是本项目自造的编号，且代码里**只被注释引用 2 个文件**
（`apps/so-cli/src/exit.rs`、`crates/so-telemetry/src/error.rs`，其余全是文档内部引用），迁移成本最低。选它动。

## 决策

### 1. 日志规则改名 `L` → `G`（logGing）

`G1`–`G6`，语义与内容完全不变（编号值一一对应）：

| 旧 | 新 | 规则摘要 |
|---|---|---|
| `L1` | `G1` | 热路径不调用 `tracing` 宏，写 `LogRecord` 到 SPSC |
| `L2` | `G2` | 级别语义；不按 tick 打 INFO |
| `L3` | `G3` | 关键事件同时进审计库与日志 |
| `L4` | `G4` | **记录错误必须带 `code` 字段** |
| `L5` | `G5` | 字段命名统一（`snake_case`、`_ts`、`_ns`） |
| `L6` | `G6` | 日志不得包含密钥与签名 |

规则编号总表变为：`H` 热路径 · `D` 确定性 · `F` 文件划分 · `E` 错误 · `I` 实现方法 ·
`A` 分层解耦 · `G` 日志 · `T` 测试 · `S` 安全。

### 2. 领域级别一律带领域前缀

| 领域 | 旧写法 | 新写法 | 含义 |
|---|---|---|---|
| 订单簿深度 | `L1` / `L2` | **`BK-L1`** / **`BK-L2`** | 一档 / 多档聚合（行业标准术语保留） |
| 风控执行位置 | `L1` / `L2` / `L3` | **`RK-L1`** / **`RK-L2`** / **`RK-L3`** | 事前 / 组合 / 守护进程 |
| 回测保真度 | `L0` / `L1` / `L2` | **`BT-L0`** / **`BT-L1`** / **`BT-L2`** | 向量化 / Bar·逐笔 / L2 订单簿 |

前缀取 crate 缩写的两字母大写形式（`so-book`→`BK`、`so-risk`→`RK`、`so-backtest`→`BT`）。
写成 **`前缀-L数字`**（连字符）而非 `BKL1`，是为了让 `fidelity = BT-L2` 这类行内引用
不至于和标识符 `BTL2` 混在一起；同时一眼可见"这是一个领域级别，不是规则编号"。

`so-book` 的模块名 **`book::L1` / `book::L2` 视图类型名不变**——那是代码标识符，
有 Rust 命名空间保护，不与文档编号冲突。

### 3. 打破"编号只增不改"的例外，并写明边界

ADR-0015 定"编号只增、不改、不复用"。本次是**唯一一次**例外，理由是
编号体系自身的存在意义（可检索、无歧义）被破坏，属于修复而非重命名。
边界：

- 今后规则编号再做任何改名，必须同样先写 ADR；
- 本次改名**只动编号字面量**，不动任何规则的语义、条目顺序或编号值（`L4`→`G4` 仍指同一条）。
- 已发布代码注释中的引用一次性改完，不保留"旧编号仍有效"的过渡期——
  保留双编号会让 `L` 的歧义继续存在，等于没改。

## 后果

- `docs/01`、`docs/02`、`docs/03`、`docs/04`、`docs/05`、`docs/07`、`docs/README.md`、
  `CLAUDE.md` 全部同步；`docs/04` §0 速查、§3.4/§3.5/§3.6/§6 反例同步。
- 代码注释 2 处：`apps/so-cli/src/exit.rs`（`L4`→`G4`）、
  `crates/so-telemetry/src/error.rs`（`§3.6 L4`→`§3.6 G4`）。
- **附带收益**：`docs/04 §3.5` 开头那段"不要混用"的免责声明可以删除——
  现在编号本身就无歧义；`docs/README.md` 术语表同理。
- `docs/03 §8.1` 的保真度表、`docs/01 §10` 的风控 mermaid 子图 ID 一并改为 `BT-L*` / `RK-L*`，
  使段落与图内标签一致。
- 风险：外部文档（`docs/venues/` 的交易所 API 说明）里出现的 `L1`/`L2` 指订单簿深度，
  若直接引用需注意本项目写作 `BK-L1`/`BK-L2`；已在 `docs/README.md` 术语表记录该映射。
