# ADR-0018：交易标的的三种形态与自主选品（so-selector）

- 状态：**已接受**（2026-11-12 拍板 4 项；同日三次补充：① 录制面改为三模式、默认 `list`，初稿"取宽如前 50"无依据已删；② S2 维持跨品类原设计，**不**新增"单策略单品类"限制；③ 实时触发定为**方案 A**：判定进内核事件循环，见 §5.1）。待实施的文档同步见「影响」
- 日期：2026-11-12
- 触发：用户澄清交易标的不是"写死一个列表"，而是三种形态；其中"程序自主选品"在现有架构里没有位置
- 相关：ADR-0001（一个账户一个策略）、[06 §3/§5](../06-data.md)、[07 §6](../07-strategies.md)

## 背景：现状把三种形态混成了一种

[06 §3.1](../06-data.md) 原话：

> 品种：按 24h 成交额前 N（初定 20）的永续合约 + 对应现货；**品种列表写在 `configs/recording.toml`**，变更有记录。

[07 §6](../07-strategies.md) 原话：

> `universe = ""  # 可选：选币型策略的币种池，如 "okx-swap-top20"；与 trade 二选一`
> 策略只交易 `trade` 列表（或 `universe`）中的品种，`watch` 中的品种只用于计算信号

两句话合起来，把"一个固定列表"当成了唯一形态。用户澄清实际需要**三种**：

| 形态 | 用户描述 | 标的范围是否变化 |
|---|---|---|
| **① 单标的** | 指定一个币，持续跟踪监测 | 不变 |
| **② 固定池** | 指定一个组合，在选中品种里交易 | 集合固定，池内挑选 |
| **③ 自主选品** | 程序自己监测哪些币适合入场（涨跌幅、波动大等） | **集合本身在变** |

①② 是"池子固定、策略在里面选"；③ 是"**池子本身在变**"。差别不是程度，是层次——
③ 需要一个独立的、能增删标的的组件，而现有架构（策略 / 风控 / 引擎）里没有任何东西承担这个职责。

## 决策

### 1. 录制面与交易面分离；录制面三种模式（默认 `list`）

**录制范围与交易范围是两个概念，分属两个进程、两套配置**：

- **录制面**：`so-recorder` 订阅哪些品种。录制器不依赖策略（A3 分层），且要在任何策略
  之前持续运行——历史数据必须连续，不能随策略启停。
- **交易面**：策略实际可下单的标的集合，由策略配置 `[symbols]`（形态①②）或选品器（③）
  决定，**是录制面的子集**；风控按交易面设限、对账按交易面归因（ADR-0001 前提）。

录制面由 `configs/recording.toml` 的 `mode` 决定（2026-11-12 用户要求"动态可选择、用配置文件"）：

| mode | 订阅哪些 | 状态 |
|---|---|---|
| `list` | 配置里的显式名单（1 个起；当前 10 个即此形态） | **默认，即现状** |
| `top` | 按规则（如 24h 成交额前 N + `pin` 固定名单）定时重算，自动增删订阅 | 后续增强：需补 `unsubscribe` 调用点；新订阅按 [gate.md §3.2](../venues/gate.md) 六步拉快照对齐 |
| `all` | 该结算币种全部在交易合约（Gate USDT 永续实测 **1065** 个，2026-11-11 instrument 快照） | 吞吐/存储与单连接订阅上限实测后再定 |

- 名单来源可以动态（`top`/`all`），但**落盘的是派生结果**：重算名单写回配置/状态文件，
  并记录规则、参数与所用 contracts 快照哈希（满足 [06 §3.3](../06-data.md)"变更有记录"）。
- **盘口漏录无法事后补录**（[06 §2](../06-data.md) 数据源表没有"事后补盘口"一项）——这是 mode 取宽取窄的真正约束。
- 初稿曾写"录制面取宽（如前 50）"：该数字无任何依据（gate.md 从未记录合约总数），**本版删除**；宽窄由 mode 与参数决定，不预设。

### 2. 新建 `so-selector`（层2），且**不是策略**

选品器是**跨策略的基础设施**，不是某个策略的逻辑：

- 放进策略里 → 每个策略各写一遍（违反 [04 §3.4 I13](04-dev-constraints.md) 复用原则），
  且无法作为独立对象验证；
- 它是**纯算法**（给定市场快照 ⇒ 输出合格标的集合），不做 I/O、不持有网络连接
  （[04 §3.4 I8/I9](04-dev-constraints.md)），所以和 `so-signal` 同属**层2**。

### 3. 接线：由 `so-engine`（层3）调用，策略**不依赖** `so-selector`

这一条是刻意的，为了**不新增同层依赖例外**：

```
so-engine(层3) ──调用──> so-selector(层2)        # 合法：高 → 低
so-engine(层3) ──把选品结果作为数据传给──> 策略、风控
```

若让 `so-strategy`(层2) 直接依赖 `so-selector`(层2)，就制造了一条**同层边**，
必须在 [04 §3.5](04-dev-constraints.md) 例外表登记——而那份表刚清空（ADR-0016）。
把选品结果当作**数据**（`so-model` 层的类型）经 `Ctx` / 事件传给策略，
依赖方向就不成问题，且符合 A4（限制只在定义处校验一次）。

所以：**选品结果的类型定义在 `so-model`（层1），`so-selector` 生产它，`so-engine` 编排它，
策略与风控只消费数据。**

### 4. 三种形态的配置

```toml
# ① 单标的：持续跟踪一个币
[universe]
mode = "single"
symbols = ["BTC_USDT"]

# ② 固定池：在给定集合内交易
[universe]
mode = "fixed"
symbols = ["BTC_USDT", "ETH_USDT", "SOL_USDT"]

# ③ 自主选品：程序决定标的集合
[universe]
mode = "dynamic"
# 选品时机（两者可同时启用）：定时重算 = 基准集；实时触发 = 达标即入
recompute_interval_secs = 3600        # 每小时重算排名
realtime_triggers = true              # 盘中达标即触发
# 指标：全部可从已录制数据算出（见「数据依赖」）
rank_by = "quote_volume_24h"          # 成交额排名
min_quote_volume_24h = 10_000_000
volatility_window_secs = 86_400       # 波动率/涨跌幅窗口
min_abs_return = 0.05                 # 24h 涨跌幅绝对值下限
max_spread_bps = 5                    # 盘口价差上限（流动性）
min_book_depth_notional = 50_000      # 盘口 N 档名义深度下限
max_symbols = 5                       # 同时交易的标的上限
```

### 5. 触发方式：定时重算 + 实时触发，但**进出规则要显式**

用户同时选了两种触发。两者的职责必须分清，否则"只进不出"会让池子无限膨胀：

- **定时重算（每 1 小时）**：算基准候选集——按成交额排名 + 波动率 + 流动性过滤，
  取前 `max_symbols` 个。
- **实时触发**：对基准候选集（或全体录制品）做快速判定，达标即入选——
  这是①"敏锐"的来源，但**必须有对称的退出规则**（跌破阈值 / 排名掉出 / 超时）。
- **滞回（hysteresis）**：进入阈值与退出阈值必须不同（如进入需 `abs_return ≥ 5%`，
  退出需 `abs_return < 3%`），否则会在阈值附近反复进出，产生无意义换手与手续费。

### 5.1 实时触发放置：**方案 A（判定进内核事件循环）**——2026-11-12 用户拍板

曾有两个候选：A＝判定代码跑在引擎事件循环内（受 H 规则约束）；B＝独立选品线程
（冷路径）算好后把结果作为事件送进内核。**定 A**，理由是 B 被本项目自己的规则排除：

1. **B 在回测里活不下去**：独立线程靠真实时钟驱动，回测里没有真实时钟——
   要么预扫数据集生成选品时刻表（"实时触发"退化成事后离线，形态③"盘中达标即入"
   的语义消失），要么回放时内联跑同一份判定（那就等于 A，只是绕了一圈）。
2. **B 制造按模式分支**：live 有独立线程、backtest 靠预生成表——正是
   "四种模式共用同一内核、内核不得按模式分支"（README 核心决策、04 §0）禁止的形态。
   A 天然是同一份代码、同一个事件序，D1（逐位可复现）自动满足。

**A 的正确写法是冷热分工**（H 规则管的是"热路径里怎么写"，不是"热路径里不能有逻辑"）：

| 层 | 干什么 | 约束 |
|---|---|---|
| **冷路径**（每小时定时重算） | 全量排名：拉 REST tickers、排序 1065 个合约、算成交额——天然要分配、要 I/O | 无 H 约束；产出**定长候选集**（前 K 名 + 版本号），作为一条事件喂给内核 |
| **热路径**（实时触发） | 只对候选集的**定长槽位**做阈值判定 + 滞回（f64 比较），位图置位/清位 | H1 预分配定长数组（入选 = 给固定槽位赋值，不 `Vec::push`）；H5 指标计算允许 `f64`；H7 时间只用 `ctx.now()`（这也是回测可重放的关键）；H8 用 `InstrumentId` 数组下标 + 位图，无 HashMap；H6 饱和运算防溢出 |

两个实施参数（定结构、值留研究期）：

- **判定节拍**：随 `futures.tickers` 的 **1s 推送**查一次（录制面已含此频道，天然节拍；
  节拍本身是选品语义的一部分，必须显式固定——同一数据不同节拍 ⇒ 不同选品结果）。
- **候选集大小 K**：配置项、定长预分配（冷路径给热路径留的预筛池，如 50–100）；
  影响"漏掉快速异动"的概率，属研究调参。

### 6. 确定性（D1）与未来函数（06 §9）

- 选品在回测中必须**逐位可复现**：[04 D1](04-dev-constraints.md) 要求在相同输入下输出相同标的集合，
  因此重算时刻、指标窗口、排序打破平局的规则都要显式固定（不能依赖输入顺序或哈希表迭代序）。
- **严禁未来函数**：t 时刻的排名只能用 **t 时刻可知**的数据。用"今天涨幅大"选品时，
  若回测里用了当日**收盘**数据去决定当日**开盘**的标的，就是 [06 §9](../06-data.md) 点名的
  "最常见的回测错误"。实现上：指标的窗口上界恒为 `ts_recv`（经延迟模型），并由
  "篡改 t 之后的数据 ⇒ t 及之前的选品结果不变"的测试守住。
- 实时触发按 §5.1 定为方案 A：判定在引擎事件循环内，受**热路径规则**约束
  （H1–H10：不分配、不加锁、不 panic；冷热分工见该节）；输出是**定长位图**而非动态集合。

### 7. 进出场必须留痕

标的被选中 / 被踢出是**策略的决策事件**，按 [06 §7.1](../06-data.md) 与 04 S 系列进决策日志与审计：
否则事后无法回答"为什么当时交易了这个币"。每次变更记录：时刻、指标值、旧集合、新集合、触发原因。

### 8. 上下架与历史

- 选中的币可能退市（[06 §5](../06-data.md)「保留已下架品种」）：选品器必须处理
  "持仓中的标的被摘牌"，交由风控与 OMS 处理，选品器只负责**不再选入**。
- 选品结果的**历史序列**本身是研究数据（用于复盘"当时为什么选它"），须与数据集一同版本化。

## 数据依赖

三种指标都能从**已录制**的数据算出，无需新增数据源：

| 指标 | 来源 | 现状 |
|---|---|---|
| 成交额 / 成交量排名 | `futures.trades` 聚合，或交易所 ticker REST | trades 已录 ✅ |
| 波动率 / 涨跌幅 | 由 trades 聚合的 Bar（[06 §6](../06-data.md) 派生数据） | 待 M2 的 Bar 生成 |
| 盘口流动性 / 价差 | `futures.book_ticker` / `futures.order_book_update` | 已录 ✅（bookcheck 已验证重建） |

## 待定（不阻塞本 ADR 落地，但实施前要定）

1. **指标阈值**（`min_quote_volume_24h`、`min_abs_return`、`max_spread_bps` 等）：
   属**调参**而非架构，应由研究流程（[07 §3](../07-strategies.md)）定，不写死在文档里。
   现有 `funding-carry-v1.example.toml` 的 `entry_threshold = 0.0002`（年化 2%）远低于
   行业常见的 cash-and-carry 可行门槛（外部资料普遍给年化 5%–8% 以上），实施前应按研究结论重定。
2. ~~实时触发的判定频率~~ **已定（2026-11-12）**：判定进内核（方案 A，§5.1），
   节拍随 `futures.tickers` 的 1s 推送；候选集大小 K 为配置项。
3. **`so-selector` 是否也服务 `Backtest`**：回测需要一个**确定性**的选品重演
   （同 ADR 第 6 条），这决定它是被引擎调用还是被回测器调用——两者共用同一实现即可，
   但调用点要在 M3 设计时确认。（§5.1 定 A 后此问大半消解：判定在引擎内，
   回测与实盘走同一段代码；剩余仅"冷路径全量重算在回测中如何驱动"一个细节。）

## 已讨论并明确不做的事（2026-11-12）

1. **不引入"单策略单品类"限制**。曾讨论"现货和合约属不同玩法、单个策略不应跨品类"；
   结论是**维持原设计**：S2 `st-funding-carry`（现货多 + 永续空）保留跨品类形态，理由：
   - 07 §1 的分类维度是**优势来源**（做市/微观结构/资金费套利/…），不是市场类型，
     "不跨品类"从来不是本项目划过的线；
   - 跨品类两条腿是 delta 中性策略的定义本身，拆开即失去意义；
   - ADR-0001 一账户一策略管的是**账户数**，不限制品类，S2 与它不冲突。
   配置侧照旧用 `[[trade_legs]]` 表达多条腿；现货腿所需的解析已备（`so-adapter-gate/src/spot.rs`）。
2. **不做全市场自动录制**（`all` 模式）直到实测数据出来：Gate USDT 永续实测 1065 个合约，
   是当前录制规模的 106 倍；`gate.md` 未记录单连接订阅上限，接入前须先查官方文档补录（04 §5.5）。
   另注意其中混有代币化股票合约（`AAPL_USDT` 等），全录=连股票永续一起录。
